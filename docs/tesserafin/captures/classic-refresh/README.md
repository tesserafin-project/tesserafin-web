# Tesserafin Classic visual refresh — owner-acceptance captures

Twelve PNGs: six views × before/after. Generated by `npm run captures`, which is **server-free** —
static-serve, real Chromium, no Tesserafin server, no network, no library data.

| File | View | Profile | Mode |
|---|---|---|---|
| `01-home-desktop-dark` | Home | desktop / pointer, 1440×900 | dark |
| `02-library-mobile-dark` | Library | mobile / touch, 390×844 | dark |
| `03-item-details-tv-dark` | Item details | TV / remote, 1920×1080 | dark |
| `04-home-desktop-light` | Home | desktop / pointer | light |
| `05-library-mobile-light` | Library | mobile / touch | light |
| `06-home-desktop-dark-reduced-motion` | Home | desktop / pointer | dark, reduced motion |

## What is actually in the picture

The real `MediaCard`, `MediaShelf`, `MediaGrid`, `Surface` and `Tabs` from `src/ui/`, rendered
through the real `resolveTokensForProfiles` → `toCustomProperties` pipeline, inside the Theme
Studio's own `PreviewCanvas`. Nothing is redrawn or approximated for the capture: a harness that
painted its own markup would produce screenshots of the harness.

`before` is `tesserafin-design/themes/classic/tokens.json` **at the merge-base with `origin/main`**,
read out of git by `tests/captures/prepare-tokens.mjs` rather than restated — so it is exactly what
a reviewer sees on the base branch, and it cannot go stale.

Fixtures are synthetic and deterministic, with no image URLs at all. That is why the cards show a
letter rather than artwork: the capture must render identically for everyone, must work with no
server, and must not leak library contents into a shared screenshot.

## Why this set is committed

`tests/captures/out/` is gitignored — it is regenerated on every run, and committing it would churn
binaries into history on each design iteration. This directory is a **snapshot taken once for owner
acceptance** of a specific change. Re-run `npm run captures` to reproduce it; replace this directory
only when a new acceptance round needs it.

## What the suite asserts alongside the pictures

A screenshot proves nothing on its own, so `tests/captures/classic-refresh.spec.ts` also checks the
things that would make one misleading:

- the harness finished loading its tokens before the shot (`data-capture-ready`), so a capture can
  never be of a half-applied palette;
- the palette reaching the DOM is the one the filename claims;
- `before` and `after` are genuinely different palettes — otherwise every pair would be identical
  and the evidence would look complete while proving nothing;
- reduced motion really zeroes `--rf-motion-duration-*` rather than only setting an attribute;
- a shelf lays out as a row of 260px items, not one full-width card.

There is deliberately **no screenshot comparison**. The whole point of the change is that the pixels
differ; a snapshot baseline would have to be updated by the same commit that changes the design,
which makes it a record of what happened rather than a check on it.
